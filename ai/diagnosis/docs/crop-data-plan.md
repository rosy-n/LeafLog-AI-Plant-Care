**crop 컷오프 실측 완료 — 0.80 확정 (2026-09-25)** — ✅
- 방법: 실내식물 221장을 쿼리로, 실제 `search_similar_cases()` 코드를 진짜 Qdrant 클라이언트(인메모리)에 적재한
  실내식물 221건 + crop 2,994건 위에서 그대로 실행(leave-one-out: 쿼리 사진 자신은 제외). 종 지정 여부 ×
  부위 지정 여부 × crop 꺼짐/컷오프 0.75·0.80·0.85 비교. 지표는 precision@5(원인 일치율)·hit@5·crop 노출도.
  (사전에 numpy로 유사도 분포와 구간별 원인 일치율·우연 대비 배율을 탐색 분석 — 이건 종/부위 필터 없는 단순
  유사도 분석이라 실제 검색 재현이 아님)
- 결과: 최고 유사도 중앙값은 실내식물끼리 0.847, crop과 0.805. crop 이웃의 원인 일치율은 0.75 미만에서
  우연 수준 이하, 0.86 이상에서 25%(같은 구간 실내식물끼리는 25~36%)로 원인 구별력이 약함. 실제 검색에서
  컷오프 0.75는 정밀도를 1~1.5%p 낮췄고(예: 48.5%→46.9%), 0.80 이상은 crop을 껐을 때와 같음(48.6%/48.8%).
  crop은 쿼리의 2~3%(0.80)에만 들어옴.
- 결론: `QDRANT_CROP_MIN_SCORE=0.80`(코드 기본값). 다만 이 평가는 **crop이 가치 있을 종(레몬·올리브 등, 실내식물
  데이터에 없음)을 평가하지 못함** — 쿼리가 전부 실내식물이고 원인이 crop에도 있는 쿼리가 70장뿐.
- 알아둘 점: 같은 종 승격은 그 종의 crop 원인이 적으면 원인과 무관하게 채워질 수 있음. 특히 올리브는 crop이
  탄저병 100장뿐이라 올리브로 종을 지정하면 실제 원인이 뭐든 탄저병 사례가 1단계로 올라옴(레몬 4개, 무화과 2개,
  한라봉 4개 원인). 필요하면 1단계 crop 몫에 상한을 두거나 종 승격을 crop 원인이 다양한 종에만 적용.

**보류 중(이번 라운드 범위 밖, 필요해지면 재검토)**
- 153번(보강 소스) 데이터 추가
- crop 데이터 상한(현재 조합당 100장)을 늘려서 재실행할지 여부
- 학교 PC의 원본 이미지·`crop_labels.xlsx` 전체(38,097행) 정리 — 재현성 위해 당분간 보관 권장,
  급한 디스크 압박 없음(900GB+ 여유)

## 배경

## 다운로드 범위 (확정)

### 525번 (메인)

**받을 것**: 작물별 `병해.zip` + `생리장해.zip`, Training(TS) + Validation(VS) 둘 다
**받지 않을 것**:
- `정상.zip` — 무병징 대조군, 우리 목적(증상 검색)엔 불필요, 용량만 큼
- `작물보호제처리반응.zip` — 농약 살포 후 반응 연구용, 병해충 진단과 무관
- `환경센서/` — 이미지 아닌 센서 로그, CLIP 임베딩 대상 아님

### 153번 (보강)

**받을 것**: 위 매핑 표에서 ✅인 9개 클래스(흰가루병 5작물 + 노균병 3작물 + 잿빛곰팡이병 1 + 탄저병 1)의 **질병 원본** 이미지만
**받지 않을 것**:
- 정상 이미지 (204,909장) — 전체 스킵
- 증강 이미지 (약 20만 장) — 원본만으로 충분, 증강본은 CLIP 임베딩 다양성에 실질적 이득 없이 용량만 차지
- 바이러스성 3종, 매핑 보류된 잎곰팡이병/점무늬병/균핵병 — 위 매핑 표의 ❌ 전부 제외

Train/Validation을 둘 다 받는 이유: CLIP은 파인튜닝하지 않고 그대로 쓰므로 과적합/데이터 누수 개념이
적용되지 않음. 대신 검색 품질 평가는 **실내식물 200장 중 일부(예: 20장)를 인덱스에서 제외하고
쿼리 전용 홀드아웃으로 남겨서** 진행하기로 함 (아래 "검증 계획" 참고).

## 검색 아키텍처 (완전 분리 컬렉션 대신 이 구조로 확정)

- 컬렉션은 하나로 유지, payload에 `domain` 필드 추가 (`"houseplant"` / `"crop"`)
- `03_search_similar.py`의 기존 species 우선순위 fallback 패턴을 domain에도 적용하는 tiered 검색:
  1. houseplant + species 일치
  2. houseplant 전체 (species 무시)
  3. crop 전체 — 원인(suspected_cause)별 신뢰도 가중치로 score 보정 후 남은 자리만 채움
- crop 도메인 point ID는 houseplant의 `image_id`(int)와 충돌 방지를 위해 `domain:image_id` 조합의 결정적 UUID로 부여 (구현 시 결정)

## 원인별 신뢰도 가중치 (crop 3단계 순위 보정용, 실측 전까지 잠정값)

숙주 특이성이 낮을수록(=농작물 사례를 믿을 수 있을수록) 가중치를 1에 가깝게. 코드는
`apps/api/app/diagnosis.py`의 `CROP_CAUSE_WEIGHTS`(표에 없는 원인은 `CROP_DEFAULT_WEIGHT=0.7`).
같은 종 crop 사례(1단계 승격)는 가중치를 적용하지 않는다.

| 원인 | 가중치 | 근거 |
|---|---|---|
| 일소현상 | 0.9 | 물리적 광 손상, 숙주 특이성 거의 없음 (확정) |
| 다량원소 결핍 / 냉해피해 | 0.85 | 병원균이 아닌 생리장해라 종 무관 (2026-09-25 잠정) |
| 흰가루병 | 0.8 | 숙주 범위 넓은 자낭균 (확정) |
| 노균병 / 잿빛곰팡이병 / 그을음병 / 총채벌레 / 응애벌레 | 0.8 | 다범성 병원균·해충 (잠정) |
| 탄저병 | 0.65 | Colletotrichum은 숙주별 종이 다른 경우가 많음 (확정) |
| 점무늬병 | 0.6 | 특정 병원균이 아닌 포괄적 증상 범주 (잠정) |
| 궤양병 / 귤굴나방 | 0.5 | 감귤속 전용 — 다른 숙주 사례로는 신뢰도 낮음 (잠정) |

## 525번 코드표 (데이터설명서·구축가이드라인 PDF 확인 완료, 2026-09-14)

샘플(`TL1_고추/병해`, disease="a7")로 시작했던 코드 미확인 문제는 AI-Hub 공식 PDF
(`식물 병 유발 통합 데이터_데이터구축가이드라인_v0.1.pdf` 표 84 "코드 정의서")로 해결됨.
`a7 = 고추탄저병`으로 확인 — 아래 매핑은 이 표 기준이며 위 "작물별로 실제 채택할 클래스" 표와
1:1로 대조 확인함 (제외 대상 4개가 정확히 a10/b2/b3/b5와 일치).

- **작물 코드**: 1=딸기, 2=토마토, 3=파프리카, 4=오이, 5=고추, 6=시설포도
- **부위 코드(area)** → `plant_part`에 직접 매핑: 1=열매, 2=꽃, 3=잎, 4=가지, 5=줄기
- **병해 코드(disease, a-계열)** — 작물+병명 1:1, 채택 11개(❌ 1개):
  a1=딸기잿빛곰팡이병✅, a2=딸기흰가루병✅, a3=오이노균병✅, a4=오이흰가루병✅,
  a5=토마토흰가루병✅, a6=토마토잿빛곰팡이병✅, a7=고추탄저병✅, a8=고추흰가루병✅,
  a9=파프리카흰가루병✅, a10=파프리카모잘록병❌(제외), a11=시설포도탄저병✅, a12=시설포도노균병✅
  → `suspected_cause`는 작물명을 뗀 병명만 사용 (예: a7 → "탄저병")
- **생리장해 코드(disease, b-계열)** — 작물 공통, 채택 3개(❌ 3개):
  b1=냉해피해✅, b2=열과❌(제외), b3=칼슘결핍❌(제외), b4=일소피해✅(→"일소현상"),
  b5=축과병❌(제외), b6/b7/b8=다량원소결핍(N/P/K)✅ → 셋 다 "다량원소 결핍" 하나로 병합
- **작물보호제 처리반응(c-계열)**: 다운로드 대상 아님(위 "다운로드 범위" 참조) — 무시
- **질병 피해 정도(risk)**: 0=정상, 1=초기, 2=중기, 3=말기 (기존에 알고 있던 값과 동일)

`part`(병징 바운딩박스, `bbox`와 별개)로 병해 발생 부위만 크롭해서 임베딩하면
`images_cropped` 실험과 같은 방식으로 CLIP 임베딩 품질을 높일 여지가 있음 — 구현 시 검토.

## 라이선스 제약 (PDF로 확인됨 — 설계에 반영됨)

데이터구축가이드라인 2.2.2절: **"모든 데이터는 2차 가공 및 배포 금지, 사용 시 출처 작성"**.
즉 원본 이미지를 우리 앱에서 사용자에게 다시 보여주면 재배포에 해당할 소지가 있음 — 위
"원본 이미지 최종 보관 위치" 절에서 이미 결정한 "crop 도메인은 이미지 없이 텍스트만 표시"가
저장 비용 절감을 넘어 **이 라이선스 조항 준수를 위해 필수**임이 이번에 확인됨.
`source_url`에 AI-Hub 데이터셋 페이지 URL(525번 dataSetSn 링크)을 넣어 "출처 작성" 요건을 충족한다.

### 왜 525/153번과 다르게 다루는가

애플망고·백향과·올리브·용과·바나나·레몬·무화과·한라봉 8개 작물 중 **올리브·무화과·레몬**은
한국에서 화분에 심어 실내에서도 기르는 관엽식물로 실제 유통됨 — `data_sample/labels_sample.csv`에도
이미 "올리브나무/흰가루병" 예시가 있다. 즉 525/153번(토마토·오이·고추 등 순수 채소 작물)과 달리
이건 "다른 숙주의 유사 병징"이 아니라 **같은 종의 진짜 사례일 수 있음** — 종 일치가 확인되면
`domain=crop`이 아니라 `domain=houseplant`로, 신뢰도 할인 없이 편입할 수 있는 후보.
(단, 이 8종이 실제로 `plant_species` 마스터에 등록돼 있는지는 DB 접근 권한이 있는 쪽에서 확인 필요 —
로컬에서는 확인 못함.)

### 스키마 — 525번과 달리 코드 해독이 필요 없음

폴더 경로와 JSON 모두에 작물명·부위명·병명이 **한글 그대로** 들어있다 (예: 이미지 경로
`.../원천데이터/001_애플망고/01_잎/003_검은점무늬병/`). JSON 구조:

```json
{
  "images": {"crops_idntfr": "001", "crops_part": "01", ...},
  "annotations": {
    "object_class_lclas_nm": "애플망고",   // 작물 (대분류)
    "object_class_mlsfc_nm": "잎",         // 부위 (중분류) — 잎/과실/줄기
    "object_class_sclas_nm": "검은점무늬병", // 병해충명 (소분류) — 그대로 suspected_cause 후보
    "bbox_info": [{"bbox_xcrdnt", "bbox_ycrdnt", "bbox_width", "bbox_height"}]
  }
}
```

`crops_part`(01=잎 등) 숫자 코드도 있지만 `object_class_mlsfc_nm`에 이미 한글 이름이 있어 쓸 필요 없음.
`plant_part` 매핑 시 "과실"은 525번의 "열매" 표기와 통일한다(같은 개념, 표기만 다름).

## 재개 시 먼저 결정할 것 (AWS 기준 — 아직 미확인)

1차 RAG 이전은 1회성 Qdrant 스냅샷 복원이라 "어디서 대량 다운로드·필터링·CLIP 임베딩을 실행할지"까지는
고려되지 않았다. 아래는 실행에 옮기기 전에 확인/결정해야 하는 것들.

- **다운로드·압축 해제 위치**: AI-hub 525번(6개 작물 병해+생리장해, TS+VS)과 153번(9개 클래스 원본만)을
  어디서 받을지. 후보:
  - **EC2**: `docs/aws-team-handoff.md`에 디스크(EBS) 용량이 명시돼 있지 않음 — 먼저 `df -h`로 여유
    공간 확인 필요. Qdrant 컨테이너·RDS 연결 등 운영 서비스와 디스크를 같이 쓰므로, 대량 zip을 그대로
    받으면 운영에 영향 줄 수 있음(스트리밍 다운로드 → 즉시 불필요 클래스 삭제 → 압축 등으로 최소화 권장)
  - **학교 PC(worker)**: 이미 CLIP 모델이 로드돼 있고 GPU가 있어 임베딩엔 유리하지만, SDXL/LoRA/Ollama와
    동시 구동 중인 환경이라 디스크·메모리 여유를 반드시 사전 확인 — 이 PC는 과거 Windows System Commit
    고갈로 장애가 난 이력이 있음(2026-08-06)
- **CLIP 임베딩 실행 위치와 Qdrant 접근 경로**: `Qdrant 6333`은 현재 **EC2 루프백 전용, 외부 개방 안 함**
  (`docs/aws-team-handoff.md` 236행). 즉 `02_build_index.py`를 학교 PC에서 그대로 돌리면 Qdrant에 못
  붙는다. 선택지:
  a) 대량 임베딩을 EC2 위에서 직접 실행 (GPU 없음 → 수만 장 규모면 CPU 임베딩 속도 확인 필요)
  b) 학교 PC에서 임베딩만 만들어 두고, 벡터를 EC2로 옮겨 업로드(예: SSH 터널로 잠깐 6333을 열거나,
     벡터를 파일로 내보내 EC2에서 업로드하는 별도 스크립트 작성)
  둘 다 지금 코드(`02_build_index.py`)는 "같은 프로세스에서 CLIP 로드 + Qdrant 업로드"를 전제로 하므로
  임베딩 생성과 업로드를 분리하는 리팩터링이 필요할 수 있음
- **원본 이미지 최종 보관 위치 — 결정됨: 저장하지 않는다.** 1차 RAG(houseplant)는 참고 이미지를
  S3 `rag-reference/<image_id>.jpg`에 올려 앱의 "RAG 검색 결과" 토글에서 작은 썸네일(32×32)로 보여준다
  (`apps/api/scripts/ingest_rag_reference_images.py`, `ConsultationScreen.jsx`의 `ragThumb`). 농작물
  도메인은 이 썸네일을 보여주지 않기로 함 — `SimilarCase.image_url`을 항상 `null`로 두면 프론트가 이미
  텍스트만 표시하도록 분기돼 있어(`c.image_url ? <Image> : null`) 코드 변경 없이 그대로 적용된다.
  장점: S3 저장 비용·업로드 파이프라인이 전혀 필요 없고, AI-Hub 데이터 재배포/재게시 라이선스 리스크도
  피한다 — 벡터 임베딩을 만드는 동안만 원본 이미지가 필요하고, Qdrant에 벡터+payload를 올린 뒤에는
  원본을 어디에도 남기지 않는다(임베딩 완료 후 즉시 폐기).
- **AWS 비용**: 대량 다운로드(수만~수십만 장, 수십GB)와 임베딩을 EC2에서 처리하면 컴퓨팅/스토리지/전송
  비용이 늘어남 — 운영 계정 예산 범위 확인 필요

위 사항이 정해지면 계획대로 다운로드 → 필터링(불필요 클래스 삭제) → CLIP 임베딩 → Qdrant 업로드 순으로
진행한다.
